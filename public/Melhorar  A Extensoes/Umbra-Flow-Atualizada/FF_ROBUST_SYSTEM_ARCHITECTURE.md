## Background & Context

### What is Google Veo 3 Flow?

Google Veo 3 Flow (available at `labs.google.com/fx/tools/flow`) is a video generation tool that creates videos from:
- **Text prompts** (text-to-video)
- **Text + Images** ("Ingredients to Video" mode)

In "Ingredients to Video" mode, users can:
- Select **1 to 3 images** from their gallery as "ingredients"
- Add a text prompt describing the desired video
- Click "Create" to generate the video

### What is the Existing Extension?

There is an existing Chrome extension ("Dotti Sender PRO") that automates sending multiple prompts to Flow. It:
- Parses a list of prompts with image references like `PROMPT 1 [5, 12]: description...`
- Automatically selects images from the gallery
- Enters the prompt text
- Clicks the Create button
- Repeats for 100+ prompts

### Why Do We Need F&F Robust System?

The existing extension works **most of the time** but has reliability issues that become critical when processing 100+ prompts automatically.

## Pain Points & Problems

### Problem 1: CSS Selector Fragility

```javascript
// Current extension uses hardcoded CSS class:
const gallery = document.querySelectorAll('.sc-fbea20b2-9');
```

**Issue:** `.sc-fbea20b2-9` is a hashed CSS class generated by styled-components. Google can change this class at any time during a Flow update, breaking the entire extension.

**Impact:** Complete automation failure with no fallback.

---

### Problem 2: No Click Verification

```javascript
// Current extension:
gallery[idx].click();
await sleep(1000);  // Hope 1 second is enough
// Continue without knowing if click worked
```

**Issue:** The extension doesn't verify if:
- The click was registered
- The correct image was selected
- The gallery closed properly

**Impact:** Silent failures - wrong images sent, prompts incomplete, bad video results.

---

### Problem 3: Wrong Image Selection

When processing 100+ prompts, if the extension clicks the wrong image:
- User doesn't notice until videos are generated
- Wasted time (videos take minutes to generate)
- Wasted quota (if Flow has limits)
- Batch integrity compromised

**Impact:** No way to guarantee correct image selection.

---

### Problem 4: Timing Assumptions

```javascript
await sleep(1500);  // Gallery open delay
await sleep(1000);  // Between actions
```

**Issue:** Fixed delays assume:
- Network speed is consistent
- Browser performance is consistent
- Flow's React rendering is consistent

**Impact:** Random failures when timing doesn't match assumptions.

---

### Problem 5: Silent Failures

When something fails, the extension:
- May continue with incomplete prompts
- Doesn't log what went wrong
- Doesn't save debug information
- User discovers problems only after batch completes

**Impact:** Lost prompts, no ability to debug or retry.

---

### Problem 6: No Recovery

If gallery doesn't open, or click doesn't register:
- Extension has no retry logic
- No fallback methods
- No ability to recover and continue

**Impact:** Single failure stops entire batch.

---

### Problem 7: Gallery Behavior Complexity

The Flow gallery has specific behaviors:
- Gallery **closes automatically** after selecting one image
- Must reopen gallery for each additional image
- Max 3 images per prompt
- "+" button disappears when max reached
- Images are buttons with background-images, not `<img>` tags

**Impact:** Complex flow requires precise state management.

## Goals & Requirements

### Primary Goal

**100% reliable image selection for automated prompt processing.**

Every prompt must either:
1. ✅ Complete successfully with **correct** images, OR
2. ✅ Fail **loudly** with complete debug info for manual retry

### Specific Requirements

| Requirement | Description |
|-------------|-------------|
| **Correct image selection** | Never send wrong image - verify every selection |
| **No silent failures** | Every failure must be detected and logged |
| **Complete logging** | Full debug info for any failures |
| **Recovery capability** | Retry failed actions through multiple methods |
| **CSS-change resistant** | Multiple fallback selectors |
| **Future-proof** | Visual detection as ultimate fallback |
| **Cross-platform** | Work on Mac and Windows |
| **Automation-friendly** | Process 100+ prompts without intervention |
| **Failed prompt tracking** | Save failed prompts for manual retry |

### Success Criteria

```
For 100 prompts:
- 99%+ complete automatically
- 0% wrong images (never send wrong image)
- 100% of failures logged with debug info
- Any failed prompts saved for manual retry
```

### Architecture Choice: Hybrid System

```

```

**Why this split?**

| Extension Only | Hybrid (Extension + Python) |
|----------------|----------------------------|
| Limited error handling | Full error handling in Python |
| No external verification | Python verifies every action |
| Hard to debug | Complete logging and state tracking |
| Single method per action | Multiple fallback methods |
| Silent failures | Every failure detected |

### The Nuclear Option: 5-Layer Defense

Instead of hoping one method works, we use **5 escalating layers**:

```
Layer 1: DOM-Based (Fast)           ← 95% of actions succeed here
    ↓ if fails
Layer 2: DOM + Retry + Fallback     ← 4% caught here
    ↓ if fails
Layer 3: Visual Verification        ← 0.9% caught here
    ↓ if fails
Layer 4: Computer Vision + Click    ← 0.09% caught here
    ↓ if fails
Layer 5: Human Alert                ← 0.01% truly unrecoverable

RESULT: 99.99% automated, 0.01% human intervention
GUARANTEE: Never silently fails, never sends wrong image
```

## The Nuclear Option: 5-Layer Defense

### Why "Nuclear Option"?

Traditional automation: "Try one method, hope it works"
Nuclear Option: "Try every method, guarantee success or know exactly why it failed"

### Layer Summary

| Layer | Method | Speed | Cumulative Success |
|-------|--------|-------|-------------------|
| **Layer 1** | DOM-based click with primary selector | ~50ms | 95% |
| **Layer 2** | Retry with multiple fallback selectors | ~500ms | 99% |
| **Layer 3** | Visual verification + screenshot analysis | ~2s | 99.9% |
| **Layer 4** | Computer vision template matching | ~5s | 99.99% |
| **Layer 5** | Human alert, log failure, skip prompt | N/A | 100%* |

*100% means every prompt either succeeds or is properly logged for manual retry

### Key Principle: Verify Everything

```
WRONG (current extension):
  click(element)
  sleep(1000)
  // Continue, hope it worked

RIGHT (F&F Robust):
  before_state = get_state()
  click(element)
  wait_until(state_changed OR timeout)
  after_state = get_state()
  verify(after_state matches expected)
  // KNOW it worked before continuing
```

## Detailed Layer Specifications

### Layer 1: DOM-Based (Fast Path)

**Purpose:** Handle the 95% of cases that work on first try.

**Speed:** ~50ms per action

**Method:**
```python
async def layer1_dom_action(action: str, selector: str, index: int = None) -> ActionResult:
    """Fast DOM-based action using primary selector."""

    # Execute via extension
    result = await extension.execute({
        "action": action,
        "selector": selector,
        "index": index
    })

    if result.success:
        # Quick state verification
        if await verify_state_changed():
            return ActionResult.SUCCESS

    return ActionResult.ESCALATE  # Go to Layer 2
```

**What it does:**
- Uses primary CSS selector (`.sc-fbea20b2-9` for gallery images)
- Direct DOM click via extension
- Quick state verification after action

**When it escalates:**
- Element not found with primary selector
- Click executed but state didn't change
- Timeout waiting for state change

---

### Layer 2: DOM + Retry + Fallback Selectors

**Purpose:** Handle cases where primary selector fails or timing is off.

**Speed:** ~500ms per action (with retries)

**Method:**
```python
async def layer2_dom_retry(action: str, index: int = None) -> ActionResult:
    """Retry with multiple selectors and exponential backoff."""

    FALLBACK_SELECTORS = [
        '.sc-fbea20b2-9',                    # Primary
        'button[class*="sc-fbea20b2"]',      # Partial class match
        '.sc-fbea20b2-6 > button',           # Parent-child
        '.virtuoso-grid-item button',        # Virtuoso container
        '[role="presentation"] button',      # Role-based
    ]

    for attempt in range(3):
        for selector in FALLBACK_SELECTORS:
            result = await extension.execute({
                "action": action,
                "selector": selector,
                "index": index
            })

            if result.success:
                # Wait for state change with timeout
                if await wait_for_state_change(timeout=2000):
                    return ActionResult.SUCCESS

        # Exponential backoff between attempts
        await asyncio.sleep(0.5 * (attempt + 1))

    return ActionResult.ESCALATE  # Go to Layer 3
```

**What it does:**
- Tries 5 different CSS selectors
- 3 retry attempts with backoff
- Waits for state change (not fixed sleep)
- Tries different DOM paths to same element

**When it escalates:**
- All selectors fail to find element
- Element found but click never registers
- State never changes after multiple attempts

### Layer 3: Visual Verification

**Purpose:** Use screenshots to verify correct element and action.

**Speed:** ~2 seconds per action

**Method:**
```python
async def layer3_visual_verification(action: str, expected_index: int) -> ActionResult:
    """Visual verification with screenshot analysis."""

    # 1. Get current state
    before_count = await extension.get_ingredient_count()

    # 2. Take screenshot of current state
    screenshot = await extension.screenshot("full")

    # 3. Find gallery region in screenshot
    gallery_region = await find_gallery_region(screenshot)

    # 4. Calculate image position in gallery
    image_bounds = calculate_image_bounds(gallery_region, expected_index)

    # 5. Verify it's the right image (fingerprint)
    image_data = await extension.screenshot("region", image_bounds)
    image_hash = compute_phash(image_data)
    expected_hash = gallery_fingerprints[expected_index]

    if not hashes_match(image_hash, expected_hash, threshold=0.90):
        log.warning(f"Image at position {expected_index} doesn't match fingerprint")
        return ActionResult.ESCALATE

    # 6. Click at calculated position
    click_x = image_bounds.x + image_bounds.width // 2
    click_y = image_bounds.y + image_bounds.height // 2
    await extension.click_at_coordinates(click_x, click_y)

    # 7. Wait for gallery to close
    await wait_for_gallery_close(timeout=3000)

    # 8. Verify ingredient count increased
    after_count = await extension.get_ingredient_count()
    if after_count != before_count + 1:
        return ActionResult.ESCALATE

    # 9. Verify thumbnail matches expected (CRITICAL)
    thumbnail_data = await extension.capture_latest_thumbnail()
    thumbnail_hash = compute_phash(thumbnail_data)

    if hashes_match(thumbnail_hash, expected_hash, threshold=0.90):
        return ActionResult.SUCCESS

    return ActionResult.ESCALATE  # Go to Layer 4
```

**What it does:**
- Takes screenshots for visual analysis
- Calculates element position visually
- Verifies image identity BEFORE clicking (fingerprint)
- Verifies thumbnail AFTER clicking (fingerprint)
- Uses perceptual hashing for size-invariant comparison

**When it escalates:**
- Gallery region not found in screenshot
- Fingerprint mismatch (wrong image at position)
- Click at coordinates didn't register
- Thumbnail doesn't match expected

### Layer 4: Computer Vision + Coordinate Click

**Purpose:** Ultimate fallback using pure computer vision, independent of DOM.

**Speed:** ~5 seconds per action

**Method:**
```python
async def layer4_computer_vision(action: str, expected_index: int) -> ActionResult:
    """Full computer vision - find and click by image template."""

    import cv2
    import numpy as np

    # 1. Take full page screenshot
    screenshot_bytes = await extension.screenshot("full")
    screenshot = cv2.imdecode(
        np.frombuffer(screenshot_bytes, np.uint8),
        cv2.IMREAD_COLOR
    )

    # 2. Load the template (cached gallery image)
    template_bytes = get_gallery_image_template(expected_index)
    template = cv2.imdecode(
        np.frombuffer(template_bytes, np.uint8),
        cv2.IMREAD_COLOR
    )

    # 3. Template matching
    result = cv2.matchTemplate(screenshot, template, cv2.TM_CCOEFF_NORMED)
    min_val, max_val, min_loc, max_loc = cv2.minMaxLoc(result)

    if max_val < 0.70:
        log.error(f"Cannot find image {expected_index} on screen (confidence: {max_val})")
        return ActionResult.ESCALATE  # Go to Layer 5

    # 4. Calculate click coordinates (center of match)
    h, w = template.shape[:2]
    click_x = max_loc[0] + w // 2
    click_y = max_loc[1] + h // 2

    log.info(f"Found image at ({click_x}, {click_y}) with confidence {max_val:.2%}")

    # 5. Click at coordinates
    await extension.click_at_coordinates(click_x, click_y)

    # 6. Wait and verify
    await asyncio.sleep(1.5)

    if await verify_selection_succeeded(expected_index):
        return ActionResult.SUCCESS

    return ActionResult.ESCALATE  # Go to Layer 5
```

**What it does:**
- Uses OpenCV template matching
- Finds exact image visually on screen
- Clicks by pixel coordinates
- Completely independent of DOM/CSS selectors

**When it escalates:**
- Template matching confidence too low
- Image not visible on screen
- Click at coordinates didn't work
- Verification failed after click

## Image Fingerprinting System

### Why Fingerprinting?

The only way to **guarantee** correct image selection is to **verify** the selected image matches the expected image. We do this using perceptual hashing.

### Perceptual Hashing (pHash)

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                    PERCEPTUAL HASHING (pHash)                               │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  Gallery Image (144x144)          Thumbnail (48x48)                        │
│  ┌──────────────────┐             ┌──────────────────┐                     │
│  │                  │             │                  │                     │
│  │   [Full Size]    │             │  [Resized]       │                     │
│  │                  │             │                  │                     │
│  └──────────────────┘             └──────────────────┘                     │
│           ↓                                ↓                                │
│     pHash: a4b3c2d1...              pHash: a4b3c2d1...                     │
│           ↓                                ↓                                │
│           └──────────── MATCH! ────────────┘                               │
│                                                                             │
│  How it works:                                                              │
│  1. Resize image to 32x32 pixels                                           │
│  2. Convert to grayscale                                                   │
│  3. Apply DCT (Discrete Cosine Transform)                                  │
│  4. Extract top-left 8x8 frequencies                                       │
│  5. Generate 64-bit hash based on median                                   │
│                                                                             │
│  Why it works:                                                              │
│  • Compares structural patterns, not pixels                                │
│  • Tolerant to: resize, compression, minor color changes                   │
│  • NOT tolerant to: completely different images                            │
│                                                                             │
│  Similarity Scores:                                                         │
│  • Same image, different size: 0.95 - 1.00 (MATCH)                         │
│  • Similar images: 0.70 - 0.90 (POSSIBLE MATCH)                            │
│  • Different images: 0.30 - 0.60 (NO MATCH)                                │
│                                                                             │
│  Threshold: 0.90 (90% similarity required)                                 │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

### Gallery Initialization

At the start of each session:

```python
async def initialize_gallery_fingerprints():
    """Capture fingerprint of every gallery image."""

    log.info("Initializing gallery fingerprints...")

    # 1. Open gallery
    await open_gallery()

    # 2. Count images
    count = await extension.get_gallery_image_count()
    log.info(f"Found {count} images in gallery")

    # 3. Capture each image
    fingerprints = {}

    for i in range(count):
        # Screenshot of gallery[i]
        image_data = await extension.capture_gallery_image(i)

        # Compute hash
        phash = compute_phash(image_data)

        # Store
        fingerprints[i] = {
            "index": i,
            "hash": str(phash),
            "image_data": image_data,  # For Layer 4 template matching
            "captured_at": datetime.now().isoformat()
        }

        log.debug(f"Fingerprint {i+1}/{count}: {phash}")

    # 4. Close gallery
    await close_gallery()

    # 5. Cache fingerprints
    save_fingerprint_cache(fingerprints)

    log.info(f"Gallery initialized: {count} fingerprints cached")

    return fingerprints
```

### Selection Verification

After EVERY image selection:

```python
async def verify_image_selection(expected_index: int) -> bool:
    """Verify the selected image matches expected."""

    # 1. Capture the thumbnail that was just added
    thumbnail_data = await extension.capture_latest_thumbnail()

    # 2. Compute its hash
    thumbnail_hash = compute_phash(thumbnail_data)

    # 3. Get expected hash from cache
    expected_hash = gallery_fingerprints[expected_index]["hash"]

    # 4. Compare
    similarity = compare_phash(thumbnail_hash, expected_hash)

    log.debug(f"Fingerprint similarity: {similarity:.2%}")

    if similarity >= 0.90:
        log.info(f"✓ Image {expected_index + 1} verified (similarity: {similarity:.2%})")
        return True
    else:
        log.error(f"✗ Image mismatch! Expected index {expected_index + 1}, similarity: {similarity:.2%}")
        return False
```

## WebSocket Protocol

### Why WebSocket?

| HTTP | WebSocket |
|------|-----------|
| New connection per request | Persistent connection |
| Higher latency | Lower latency |
| Slow failure detection | Instant disconnect detection |
| One-way (request/response) | Bidirectional (real-time) |

### Connection

```
Extension → Python: Connect to ws://localhost:9999
Python → Extension: {"type": "connected", "version": "1.0.0"}
```

### Heartbeat

```
Every 5 seconds:
Python → Extension: {"type": "ping", "timestamp": 1234567890}
Extension → Python: {"type": "pong", "timestamp": 1234567890}

If no pong within 10 seconds: Connection considered dead
```

## Selector Strategy

### Why Multiple Selectors?

Google can change CSS classes anytime. Having multiple fallback selectors ensures one of them will work.

### Selector Definitions

```python
SELECTORS = {
    "gallery_image": [
        # Primary: Current known class
        {"type": "css", "value": ".sc-fbea20b2-9", "priority": 1},

        # Fallback 1: Partial class match
        {"type": "css", "value": "button[class*='sc-fbea20b2']", "priority": 2},

        # Fallback 2: Parent-child relationship
        {"type": "css", "value": ".sc-fbea20b2-6 > button", "priority": 3},

        # Fallback 3: Virtuoso container
        {"type": "css", "value": ".virtuoso-grid-item button", "priority": 4},

        # Fallback 4: Buttons with background in gallery area
        {"type": "css", "value": "[class*='virtuoso'] button", "priority": 5},
    ],

    "add_button": [
        # Button with "add" Material icon
        {"type": "icon", "value": "add", "priority": 1},

        # CSS near textarea
        {"type": "css", "value": "#PINHOLE_TEXT_AREA_ELEMENT_ID ~ button", "priority": 2},

        # Custom: leftmost button with add icon
        {"type": "custom", "value": "leftmost_add_button", "priority": 3},
    ],

    "create_button": [
        # Button with "arrow_forward" Material icon
        {"type": "icon", "value": "arrow_forward", "priority": 1},

        # Button with "Create" text
        {"type": "text", "value": "Create", "priority": 2},

        # Submit button
        {"type": "css", "value": "button[type='submit']", "priority": 3},
    ],

    "textarea": [
        # ID selector (most reliable)
        {"type": "css", "value": "#PINHOLE_TEXT_AREA_ELEMENT_ID", "priority": 1},

        # Placeholder text
        {"type": "css", "value": "textarea[placeholder*='Generate']", "priority": 2},

        # Custom: largest textarea
        {"type": "custom", "value": "largest_textarea", "priority": 3},
    ],

    "ingredient_thumbnail": [
        # Button with background-image and close icon in presentation area
        {"type": "custom", "value": "ingredient_with_close_icon", "priority": 1},

        # CSS in presentation area
        {"type": "css", "value": "[role='presentation'] button", "priority": 2},
    ],
}
```

### Selector Failure Detection

```python
async def find_element(element_type: str, index: int = None) -> Element:
    """Find element using fallback selectors."""

    selectors = SELECTORS[element_type]

    for selector in selectors:
        try:
            element = await try_selector(selector, index)
            if element:
                log.debug(f"Found {element_type} using {selector['type']}: {selector['value']}")
                return element
        except Exception as e:
            log.debug(f"Selector failed: {selector['value']} - {e}")

    # All selectors failed
    raise SelectorError(f"Cannot find {element_type} - all selectors failed")
```

## Execution Flow

### Flow Gallery Behavior (Important Context)

Based on research of the actual Flow interface:

1. **Gallery opens** when clicking "+" button
2. **Gallery contains up to 24 images** without scrolling
3. **Clicking an image CLOSES the gallery automatically**
4. **Image appears as thumbnail** in prompt area
5. **"+" button reappears** for next selection (until max 3)
6. **After 3 images**, "+" button disappears

## Troubleshooting

### "Cannot connect to server"

1. **Check Python server is running**
   ```bash
   # Should see "Waiting for extension connection..."
   ```

2. **Check port 9999 is available**
   ```bash
   # Mac
   lsof -i :9999

   # Windows
   netstat -an | findstr 9999
   ```

3. **Check firewall isn't blocking localhost**

### "Gallery not found"

1. **Ensure you're on Flow page**
   - URL must be `labs.google.com/fx/tools/flow`

2. **Try refreshing the page**

3. **Check if Flow UI updated**
   - CSS classes may have changed
   - Check console for selector errors

### "Fingerprint mismatch"

1. **Gallery order changed**
   - Click "Re-initialize Gallery" in extension

2. **Images were modified**
   - Re-upload images to Flow
   - Re-initialize gallery

3. **Check debug screenshots**
   - Compare expected vs actual images

### "Layer 4 template matching failed"

1. **Update template images**
   - Capture new screenshots of UI elements
   - Save to `templates/` folder

2. **Adjust threshold**
   - Lower `template_match_threshold` in config (not recommended)

3. **Check debug folder**
   - Review screenshots to understand failure

## Grok AI Auto-Fix System (v1.4.0)

### Error Categories

| Category | Detection Pattern | Auto-Fix? |
|----------|-------------------|-----------|
| **Policy** | "violate our policies", "usage guidelines" | Yes |
| **Timeout** | No response after 50s | No (retry) |
| **Server** | "Something went wrong", "server error" | No (retry) |
| **Rate Limit** | "Too many requests", "quota exceeded" | No (wait) |
| **Generation Fail** | "can't generate", "cannot generate" | No (retry) |
